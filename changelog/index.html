    Changelog¶

    v1.47.1 (November 2026)¶

    • What each compute node's memory holds (node_disks, memory = true by default; table node_memory): the collector's login to each node, every half hour, also reads /proc/meminfo. Slurm's FreeMem is MemFree, which counts the file cache as used, so a node left idle after a long job read as nearly full: spdr01 showed 82% in use with nothing allocated and a load of 0.2. Total less MemAvailable is what programs hold; the cache is kept apart. A node's timeline draws "Memory in use by programs" from it, in place of the cache-counted line, where it is read. The Console's Nodes page uses it in fix 116.
    • tests/test_node_disks.py: a node answering here now gives its memory too.

    v1.47.0 (November 2026)¶

    • Which jobs (nomad edu me, the Console's Recommendations and My Activity): each recommendation carries the jobs it was found in, newest first, at most 50 (jobs): each one's ID, site, partition, name, when it ended and how, its score, and what it asked and used for that dimension (asked, used, unit; for GPUs busy_pct). A "Jobs that failed" card lists the jobs that failed. The text output names the first five ("Jobs: 4521, 4519 … and 3 more"). From a user meeting: people wanted to know which of their jobs a card meant.
    • The time limit counts a quarter ([edu.weights]): an overall score (a job's, a person's, a week's, a group's) is the dimensions counted by their weights, CPU, memory and GPU 1, I/O 0.5, the time limit 0.25. Before, all counted the same, and a generous limit, which mostly makes the job itself start later, pulled the overall down as much as idle cores or memory, which keep others waiting. Every overall is worked out when it's shown, so the history moves with the weights. nomad config check says what's wrong with an [edu.weights] table. Each issue carries its dimension's weight; nomad edu me --json has weights.
    • Time Limit (was Time Estimation): "Ran 1h of the 1d 0h it asked for (4%). A limit closer to how long it runs lets Slurm start it sooner, in a gap between other jobs; the limit doesn't change how fast it runs." A job stopped at its limit: "Stopped at its time limit (1h) before it finished". docs/proficiency.md had the time score's old formula; it now has the bands the code uses.
    • Cores and memory first: within a cluster and partition, a "Jobs that failed" card, then the dimensions that count fully, then those that count less (I/O, the time limit), each by severity.

    The Console's part is fix 114 (the jobs under each card, linked to their pages; the cards that count less under "Also worth a look"; the weights said wherever an overall is explained).

    v1.46.0 (November 2026)¶

    • Cores left idle (idle, now asked by default with failure): a completed job of 2 cores or more that ran 5 minutes or more and was measured, which on average left more than [ml.train] idle_threshold (0.5) of the cores it asked for unused. These are the jobs the Recommendations judge for cores, judged the same way, matched to job_summary as they match it. Time unused (waste) stays available: at the University of Richmond half the completed jobs used under 1% of the time they asked, and 89% counted as wasted even at 0.9, so its AUCs said little. Each of idle and waste carries its spread (what share of the cores or the time the jobs used), counts only.
    • Ranges ([ml.train] bootstrap, 1000 resamples): the 95% range of each model's AUC and of the difference between them, paired (the same held-out jobs for both in each resample), on all columns and without partition and cluster.

    v1.45.1 (November 2026)¶

    • A fair comparison. The first run on real jobs had the logistic regression ahead of TESSERA for failure (AUC 0.87 against 0.59). TESSERA had been handicapped: partition and cluster reached it as plain numbers, and its default similarity (simpson) cuts each feature into three equal-width bins. Both models now get partition and cluster as one column per value, and TESSERA's similarity is set in [ml.train.tessera] (similarity, default euclidean on scaled features; n_bins; k_neighbors). On made-up jobs where partition decides failure, TESSERA went from 0.70–0.81 to 0.92–0.96, level with the logistic regression.
    • What partition and cluster carry ([ml.train] compare, default true): each model is also measured without them, and the logistic regression with them alone.
    • The spread of used time, for choosing waste_threshold: how much of their asked time the completed jobs used, at the tenth to nine tenths of them, and how many count as wasted at 0.5, 0.6, 0.75 and 0.9 (counts only). On the first run 99% counted as wasted at 0.6, so waste's AUCs meant little.
    • Training worker: two passes asking at the same instant never both take the same request; nomad ml work's lines reach the journal as they are said (line-buffered under systemd), without matplotlib's font-cache notices; docs/ml-training.md puts the worker's environment in /opt/nomad-ml, since SELinux keeps a system service from running programs in a home folder.
    • Data readiness's recommendation points to Train… (or nomad ml ask) rather than only nomad train.
    • nomad facts node: on a cluster whose Slurm doesn't allocate memory (SelectTypeParameters without _Memory), the memory series carries a note saying so, which the Console's node timeline shows, instead of the "Memory allocated" line simply being absent.
    • The hub keeps a training result's summary six levels deep (it kept four, which would have dropped 1.45.1's comparisons).

    v1.45.0 (November 2026)¶

    • Training the model from the Console (nomad.learn; nomad ml; [ml.train], [ml.worker]; docs/ml-training.md). An administrator asks on Data readiness; a worker with a GPU asks the Console every 5 minutes over HTTPS with its own key (nomad ml work, nomad ml timer), takes the request, trains TESSERA (tessera-ml 0.3) and a logistic regression, and sends back how well each ranked the newest jobs (held out: given to TESSERA as unknown, learned from by nothing) and the scores of those and of the jobs running or waiting. Predicts failure and waste. What leaves the hub: per job, only what Slurm was asked, as numbers, and what became of it; never a person, job name or ID, partition or cluster name. Requests and results in ml.db (beside lab_check.db). One request at a time; a run not heard from in stale_minutes is given up. nomad ml check on the worker says what the Console answered and whether TESSERA can train there (its version, PyTorch's, the GPU). The worker never follows a redirect, so a sign-in page in front of the Console is said, and never sent the key.
    • Advice about size from jobs that completed (nomad edu me, the Console's Recommendations and My Activity, the job notices). Cores and GPUs are worked out from jobs that completed, memory from those that completed or ran out of memory, time from those that completed or reached their limit: a job that failed early used little because it never got to its work, and three such jobs had been enough to advise "52 cores → 2" and "12 days → 2:30". Each issue carries how many of the place's jobs completed and how many failed (completed_jobs, failed_jobs). Where most of the measured jobs on a cluster and partition failed (at least 2), a "Jobs that failed" card (failed) leads that place's cards instead of advice to ask for less.
    • nomad config check no longer calls [console.labs] accounts an unknown setting: the account requests' table (1.42.0) was always read.

    v1.44.0 (November 2026)¶

    • Request numbers, as a ticket system's (nomad.tickets; [console.tickets] prefix, digits). Every account request has a number, ARC-0012: on the PI's card, first in the subject of both emails (so a reply keeps it), on the Admin page and in the log. Requests made before keep theirs (#12 is ARC-0012). The numbers are one sequence, kept in lab_check.db, which other kinds of request will share.
    • Finding a request: nomad lab accounts list --find TEXT and show ARC-0012; by its number, or a NetID, a name, a lab or the PI who asked. close takes the number too.
    • The account-requests report (nomad lab accounts report --since --until [--cluster] [--json | --csv]): the requests asked in a period and what became of each account as of now, in all, by cluster, lab and month; days from asked to made (median, 9 in 10 within, longest, and which); what is still to make now and the oldest. --csv is one row per account for a spreadsheet (text a spreadsheet would run as a formula is kept as text).
    • Data unchanged for a year, one list with its cases (nomad.storage.cold; nomad storage cold; [console.cold_data]). Everyone holding at least min_tb unchanged a year on a path, on every scanned server (copies apart), with their last job, labs, PIs and what the lab check said of them. Each can become a case (ARC-0013, the same sequence) that moves from to contact, contacted, moving it, to moved or kept (and why), with notes. No alert for each person: a weekly email to Research Computing (digest --send, timer) says first any path nearly full with data on the list, then what is new, the open cases and those not updated lately.
    • Usage report, section 15: accounts asked for by PIs, read from the requests (lab_check.db, where [console.labs.check] db keeps it, else beside the database): requests, labs, PIs and people counted, accounts made, not made, withdrawn and still to make, days to make them, by month. No lab, PI or person is named; run as the account the Console runs as (lab_check.db is its own), else "not measured".

    v1.43.0 (November 2026)¶

    • Acting on an interactive server's sessions (nomad.interactive_admin; nomad interactive sessions|stop|clear|restart; four actions, on sites). Suspend a person's RStudio session (Workbench's own suspend-session: R saves it, and it comes back when they next open RStudio), stop their Jupyter server or kernel as them, clear every session idle so many hours, restart RStudio or JupyterHub. Each is a dry run unless applied, does only what sudo already lets the account do (asked first with sudo -n -l), checks that the process is that person's session and the very one looked at, and is logged. Restarting JupyterHub says how many people's servers it stops, and needs that number. Off until [actions] interactive = true. The Console's part is fix 104.
    • When each session was last busy (interactive_state.busy_at): the interactive collector keeps it, for what clear calls idle, and writes it for the hub in interactive_idle (a row for each open session, changed only when it is busy again), so the Console shows how long each session has been idle.

    v1.42.0 (November 2026)¶

    • A lab's PI asks for accounts (nomad.account_requests; nomad lab accounts). On My lab, a PI types or pastes NetIDs, addresses or names, or gives a table (CSV, tab-separated, Excel), and picks the clusters. Before anything goes to Research Computing, nomad says who each one is from the campus directory: found, with their name; several people of that name (the PI picks); not found; already has an account there (nomad has their jobs, logins or groups); already asked for. The request is emailed to notify; ARC closes each account, made or not made and why, and the PI is emailed (review_to while set). Every request and close is kept, with who and when: the record ARC has no ticket system for. nomad makes no account itself. The Console's part is fix 102.
    • The campus directory, as a service account (nomad.directory; [directory]). Through ldapsearch, over ldaps only, with the password in the nomad account's own file and handed over in a file deleted after, never on a command line. Only a person's NetID and name are read, and only of what a PI typed.

    v1.41.0 (November 2026)¶

    • One node over a window (nomad.facts.node; nomad facts node SITE NODE). What Grafana answers with a query, answered once: a node's cores allocated and load, memory allocated and held, GPUs busy (DCGM), GPU memory and temperature, the hottest CPU or board sensor, the CPU clock as a share of its top speed and the fullest local disk, at one step for the whole window; and what happened on it: drained, draining, down and back (Slurm's reason for staff), gaps in the readings, jobs started and ended, out-of-memory kills, power events, alerts and declared maintenance, with a summary in sentences. Staff see every job on the node and whose; anyone else their own, the others counted. The Console's node timeline (fix 101) reads it, and a local AI model will.

    v1.40.0 (November 2026)¶

    • The gate through another host (gate_jump in a site's [[hub.sites]]; nomad gate jump-key). A cluster the hub reaches only through another host (vadur, through jonimitchell) can have the Console's Submit page and live jobs too: the gate's own key, with the same strict settings, opens a forwarded connection to the cluster's ssh on that host (ssh -W), and its line there allows nothing else (no terminal, no command, forwarding only to the cluster's address, from the hub's). The hub's own ssh settings are still never used. Tried against real sshd: the gate answers through the jump; the jump key gets no shell and can forward nowhere else.
    • How often the hub reads the sites, from nomad.toml ([hub] sync_interval_minutes; nomad sync timer). --apply writes a drop-in for nomad-sync.timer: every that many minutes, two minutes after the five-minute marks the sites read themselves on. nomad config check says when the value isn't minutes that divide an hour. Five minutes (from twenty) costs no storage and about 2% of one of the hub's cores; a job that started shows as running in the Console within minutes.

    v1.39.1 (November 2026)¶

    • The weekly email, as people read it. What is alike is one note: the times of one kind of login-node use (five shown, the rest on My activity), or one kind of asking for too much over a person's partitions with an #SBATCH line each; why it matters and the better way are said once a note, not under every entry (a week's email had the same paragraph eight times). Sizes and times in words ("asked for 1 day; they used about 50 min", "32 GB", "8 cores") instead of "2988.5 seconds" and "4903.61 MB"; the reason lines are the email's own, without contractions. The subject counts notes.
    • sshd-session is what a login node is for. Newer OpenSSH (9.8+) runs each login and transfer as sshd-session (and sshd-auth): skipped like sshd and scp, on My activity and in the email.

    v1.39.0 (November 2026)¶

    • A weekly email to each person about their own use (nomad notices, docs/notices.md). Once a week at most, and only with something new: what of theirs a login node's monitoring caught (1.38.0), and a pattern of jobs asking for far more than they use (most of at least 5 jobs on a partition, high or critical), with the better way and a link to My activity. Never the same thing twice (a jobs pattern again after 30 days if it still holds). On for everyone by default: a person turns it off on My activity in the Console (Console fix 96), an admin for them with nomad notices set NETID off --apply. Accounts only for a course are left out (courses = true includes them). Review first: while review_to is set every email goes there; people get them only once [notices] review_to = [] (report.toml's review_to holds them until then; the lab check's never decides them). nomad notices mail [--send], nomad notices timer [--apply] (Mondays 09:10 from systemd). The record is notices.db beside the combined database.

    v1.38.0 (November 2026)¶

    • Heavy use of a login node, told to the person. What the per_user collector flags on a login node was read only by the admins' insights brief; the person who ran the work never heard of it. nomad edu me now ends with "On the login nodes": what ran, on which cluster, when, for how long and how much, why it matters on a machine everyone logs in to, and the better way (Submit a job, an srun session, a build or an archive inside a job), without blame. The Console's My activity and Home show the same (Console fix 95). What is told is set in [notices.login_node]: one program holding half a core or more for 15 minutes, someone's programs together keeping two cores busy or holding 32 GB, one program holding 16 GB, a large transfer; never the 10%-for-5-minutes rule (a pip install reaches it), and never programs that move data in or out (scp, sftp-server, rsync, sshd). One entry per program run, the last 30 days, local time. nomad config check says what is wrong in the section.

    v1.37.0 (November 2026)¶

    • A site watches its hub. The hub said so when a site stopped answering; nothing said so when the hub itself stopped (its disk died one night, and every page showed that evening's data until someone looked). Each time the hub reads a site it now leaves a note there (its name, when it read), and after each collection the site's own nomad checks: a hub that read it regularly (twenty times over a day) and has not for [alerts.hub] after_minutes (60; three of its usual intervals when that is longer) is said so through the site's own alert backends, source hub: a warning, critical after a day, once, again when worse, then every reminder_hours. Only silence the site saw counts: after its own outage the hub has the time again. A hub silent for a week is taken as retired. Starts a day after the hub and the site are on 1.37.
    • Declared maintenance: nomad maintenance start SITE --until WHEN --reason WHY [--from WHEN], nomad maintenance end SITE (both show what they would do; --apply does it), nomad maintenance (now, coming, lately). SITE is one of the hub's sites, all, or hub. While a site's window lasts, and [hub] maintenance_grace_minutes (60) after it, the hub holds every alert it raises about that site, and the site's own nomad holds its alerts too (the hub tells it at once, and with each read; [alerts] maintenance_hold = false at a site keeps them coming; the hold lapses a day after the hub's last read). What still holds afterwards is raised then, as news, with when the window ended; what came and went during the window is not sent afterwards. For hub, the sites don't report the hub as silent. A window always ends (--until, at most [hub] maintenance_max_days, 14); one per site at a time. The windows are kept in maintenance.json beside the hub's combined database.
    • nomad sync says what is in maintenance; its "not synced" alerts name their site, so one in maintenance is held.
    • The Console may ask for them: actions maintenance (what is declared), maintenance.start and maintenance.end (a dry run unless applied, as a node's drain).

    v1.36.0 (November 2026)¶

    • nomad lab check names --set: the PIs' names for the lab check's email, found and asked for in one command. nomad looks for each missing name on the system, read-only: the account's full name, then the directory without a login ([console.labs.check] directory, else the system's ldap.conf; an anonymous ldapsearch -x, never a password). It shows what it found for you to keep, asks for the rest one at a time (a name, Enter for later, or - when the group is not a lab: it goes to [console.labs] not_labs), shows the change, and writes it only when you say so, with nomad's careful edit of nomad.toml (a backup, owner and mode kept, nothing else changed, never over someone else's edit). It also says when nomad.toml can be read by anyone on the machine.
    • --from FILE [--apply]: the answers from a file (the names table, or lines NETID,First Last); --no-lookup: ask only.
    • nomad lab check name NETID First Last [--apply] for one PI later (First | Last for a last name of more than one word; --remove).
    • New setting: [console.labs.check] directory ("auto", false, or { uri, base, id }).
    • nomad.toml edits can write inline tables ({ first = "Maria", last = "de la Cruz" }).

    • Text files edited from the Console, besides job scripts: a person's own .py .R .m .jl .sh .in .inp .com .gjf .yaml .yml .json .toml .cfg .conf .txt .md (TEXT_EXTENSIONS), UTF-8, at most 256 KB, never hidden, no NUL. nomad-gate read --path PATH gives one (only with serve --edit, as save); save takes them too, with every safeguard it has for scripts (the text opened, the earlier text kept, the group and access lists, the folder as it really is).     • A node that fails every job at start ([alerts.node_jobs], raised by the node_state collector): one where, among the jobs that started there in the last hour, at least 5 failed within a minute and they are at least 80% of them, while the very same work (the array's other tasks, the person's jobs of the same name) ran on other nodes and hardly failed there.
