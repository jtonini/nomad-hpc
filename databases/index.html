    nomad's own databases¶

    nomad keeps what it collects in SQLite databases: each site's, the hub's combined one, and a few helpers beside them (lab_check.db, notices.db, ...). Since 1.61.0 it watches them too: how big each is, how fast it grows, the space a vacuum would give back, and old copies left beside them.

    The databases collector¶

    On by default wherever nomad collects. Every every_hours (6) it reads each database here:

    • its size, its write-ahead log, the free space inside it (what a vacuum gives back) and the free space on its disk;
    • each table's highest row number, so the rows each table writes a day can be told without reading the tables (measuring a table's bytes reads every page: minutes for a database of gigabytes).

    The readings (db_files, db_tables) go to the hub with the rest, so the Console's Infrastructure page shows every site's databases. It warns (an alert, database_growth) when a database grew more in a day than alert_growth_mb (1 GB) and, once it has a week of days, more than growth_factor (4) times its usual day: a collector writing far more than it should is found the day it starts. A disk filling up is the disk collector's alert already (its forecast).

    [collectors.databases]
# enabled = true
# every_hours = 6
# stray_days = 14            # another .db not written this long is an old copy
# alert_growth_mb = 1024     # a day's growth that warns (and growth_factor times the usual)
# growth_factor = 4
# incremental_vacuum = true  # weekly, where a database is set for it
# keep_days = 400            # these readings

    Which databases: the site's ([database] path, else nomad.db in [general] data_dir), the hub's combined one where [hub] lists sites, the helpers, and any other *.db in those folders. One not written for stray_days is an old copy (a copy made before an upgrade or a restore); one with no rows at all is empty.

    nomad db status¶

    nomad db status              each database here: size, growth a day, free inside and on its disk
nomad db status --tables     and each table's size and rows a day (slower)
nomad db status --sites      on the hub: every site's, as each last read them

    nomad db tidy¶

    Removes old copies and empty databases. An old copy goes only when the live database (the site's, or the hub's for a hub's copy) holds everything nomad keeps that it holds:

    • every job and every measured job (a pending array's placeholder, an id with [..], is replaced by the array's own tasks: counted, not held against it);
    • a table that keeps one row per thing (groups, monthly usage, job accounting) by what each row is about, not by its date (a membership that ended since is counted, not held against it);
    • the lab machines' process records one by one;
    • any other table with a time column: at least as many rows up to the copy's last day; tables nomad trims on purpose (temperatures, raw samples) aside.

    Otherwise the copy stays and what only it holds is said. Without --apply it only says what would go. nomad db tidy FILE checks one file; one that nomad uses is never removed.

    nomad db keep¶

    The keep rules, below.

    nomad db vacuum¶

    SQLite doesn't give back the space of deleted rows by itself. Set for incremental vacuuming, a database gives it back page by page, moving pages, never rows, and the collector does it once a week. Setting a database for it takes one whole vacuum:

    nomad db vacuum --full            what it would give back
nomad db vacuum --full --apply    once: set for incremental vacuuming, vacuumed whole
nomad db vacuum --apply           from then on, by hand (the collector does it weekly)

    A whole vacuum needs about twice the database's size free on its disk: SQLite writes a copy of the database and a journal of the pages it replaces, both beside the database (1.63.2: left to itself SQLite puts the copy in /var/tmp or /tmp, often a small partition, and stops with "database or disk is full"). It holds the database while it runs (minutes for gigabytes: a collection or a hub's sync then waits or tries again). It may also give rows new numbers, which the hub's incremental sync goes by, so it takes the site's change log out: the hub copies that site's database whole at its next sync, then goes on as before.

    Keeping less: the keep rules (1.63.0)¶

    nomad keeps every reading in full for detail_days (90). After that it keeps less detail, but never drops history outright. Readers keep reading the same tables, and find hours or days where the readings are older. Part 1 covers the tables nothing in nomad reads in full detail beyond a few days:

    Table Full detail After that, kept for good
    mpstat_core (CPU busy per core) 90 days one row per core an hour, holding the hour's averages, for hourly_days (365); then one a day
    iostat_device (disk activity per device) 90 days the same, per device
    workstation_mount_state (lab machines' mounts) 90 days for each day: the day's last run, each machine and mount's last reading, and its last reading that was not mounted or not answering (a day with trouble still says so)
    collection_log (collector runs) 90 days each collector's day in collection_log_daily (runs, failures, records, first and last run, the last error), and each collector's very first run as it was

    A day's average is the average of its hours. Jobs, their summaries, job accounting, groups, alerts and monthly usage are never trimmed.

    Part 2 (1.64.0): the tables reports read over terms and years. These keep every reading for report_detail_days (395, 13 months), so a term report, a condo report or a year's figures read every reading of any period that began in the last 13 months. After that the tables keep one reading every sample_minutes (15), as it was taken, so every report and page goes on reading them as before:

    Table Full detail After that, kept for good
    node_state (cluster nodes' state) 13 months one check of the cluster every 15 minutes, with every node's reading at that moment, so a count of nodes down (an outage) still means what it did
    gpu_stats (GPUs) 13 months one reading per GPU every 15 minutes
    vmstat, iostat_cpu (a machine's processor and memory) 13 months one reading every 15 minutes
    workstation_state (lab machines) 13 months one reading per machine every 15 minutes
    workstation_user_snapshot (people's sessions on lab machines) 13 months each person's last reading on a machine every 15 minutes, and every reading where one of their sessions ends or begins, with each session's reading with the most memory in use (1.64.1): the sessions, their length and processor time stay exactly as they were; long runs in them are found at 15 minutes
    interactive_sessions (sessions on interactive servers) 13 months removed, where the server's daily totals (interactive_daily) had begun by that day: those totals keep each person's day
    workstation_process_record (programs run on lab machines) 13 months removed: nothing in nomad reads it

    A reading that stands for 15 minutes counts for 15 minutes: the term report weighs each day by the time its readings cover, so a period with older days thinned and newer ones in full gives the same shares and hours. What is lost is detail inside the 15 minutes (a node down for five minutes between two checks, the highest run queue of a minute).

    Where it runs. On the database nomad collects into: each site's, and the hub's own (not the hub's combined database, which follows the sites).

    The first time: nomad db keep --apply. - Without --apply it says what is due, table by table. - With it, each table with more than keep_max_rows (1,000,000) rows due is first taken out of the change log, so the hub copies that table whole at its next sync rather than one row at a time. - Then the database is vacuumed, to give the space back. A database not yet set for incremental vacuuming gets a whole vacuum (as nomad db vacuum --full), and the hub copies it whole once. --no-vacuum leaves the space free inside, for its new readings. - The hub's combined database gets its own space back later, with nomad db vacuum --full on it, once the sites' copies have reached it.

    After that, once a day. The databases collector goes through the rules once a day on that database, a day's worth at a time, through the change log as any other change. It does this only once nomad db keep --apply has run there, and leaves any table with more than keep_max_rows rows due for nomad db keep --apply again. A run stopped part way goes on from the day it got to. A rule new to a database (part 2's, on a database part 1 went through) waits until nomad db keep --apply has gone through it there once; nomad db keep names the tables waiting, and for each table with nothing due yet, the day its first readings become due.

    [collectors.databases]
# keep_rules = true          # the collector's daily run (after nomad db keep --apply once)
# detail_days = 90           # full detail this long (part 1)
# hourly_days = 365          # then hours this long, then days (CPU per core, disk per device)
# report_detail_days = 395   # full detail this long (part 2: the tables reports read; 1.64.0)
# sample_minutes = 15        # then one reading this often: 5, 10, 15, 20, 30 or 60 (1.64.0)
# keep_max_rows = 1000000    # a daily run with more due waits for nomad db keep --apply
# [collectors.databases.keep]          # a table's own, to differ
# mpstat_core = { detail_days = 180 }

    What it did is kept in keep_runs (when, how, which table, rows before and after), and where each table has got to in keep_marks.
